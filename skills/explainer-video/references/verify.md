# 检查清单

用户只会看成片，看不到过程。所以每个问题都要在交付前被你自己发现。

## 0. 方案页（第 6 步）

交给用户之前，自己先打开 `plan/index.html` 看一遍：
- [ ] `lint_project.py` 没有 FAIL，WARN 都看过（方案页底部有列表）
- [ ] 问题、主线、回答三句话写了，而且结尾的回答真的回答了问题
- [ ] 钩子镜头和核心机制镜头至少各有一张真实渲染的风格帧；用到的每条路线至少一张
- [ ] 风格帧里的主体和全片其他镜头是同一个东西（同一个模型、同一张贴图），不是另画的
- [ ] 待确认事项每条都有推荐项，而且都是会改变片子的决定，不是“要不要继续”
- [ ] 估算的时长在要求的 ±10% 以内；超了就先删句子再给用户看
- [ ] 有试听的话，读音、语速没问题

## 1. 每个镜头做完后（第 8 步）

用 `capture_frames.mjs --stills` 出开头、中间、结尾三帧，逐张看：
- [ ] 主体在画面里，没有被裁掉，没有贴边（离边缘至少 7%）
- [ ] 文字没有溢出，没有重叠，没有进入底部字幕区；字号不小于画面高度的 1/24
- [ ] 颜色、字体、角标符合 `style.json` 的规定，主色不超过三种
- [ ] 画面讲的就是这几句口播在讲的事。核对一下口播说到 X 的那一刻，画面上 X 是否已经出现或者高亮
- [ ] 读数和标注的数字和事实表或计算模型一致
- [ ] 证据角标正确：宣称、估算、复原想象、模拟、AI 生成画面
- [ ] 这一帧和前后镜头接得上（匹配剪辑的话，比较一下首尾帧）
- [ ] R1 镜头：零件没有互相穿过；放大 4 倍看，细节没有缺失
- [ ] R1 镜头：口播说到的部件都在模型里，并且在说到时看得见（拆开、剖面或推近），不是只转一个外壳；`render_shot.sh` 报的零件数不少于 40
- [ ] 2D 场景里出现的主体，用的是从 3D 模型抠出的贴图（`sprite.sh`），和 3D 镜头是同一个东西
- [ ] 正式渲染完的片段：看 `render_shot.sh` 导出的 `clip.mp4.check.png`，确认画的是你的物体和你的机位。静帧预览对，不代表正式渲染也对
- [ ] 机器在动的镜头：运动速度和模型一致，比如秒针每秒走 8 小步、四轮每分钟一圈；慢放倍数写在角落的读数里
- [ ] 分镜里标了 `risks` 的镜头，按 `directing.md` 第 8 节在指定时刻出帧检查过：关键动作看前中后，跨句连续看句子交界的两侧
- [ ] 画了力的镜头，按 `directing.md` 第 6 节逐条过了一遍
- [ ] 变化的后果（`result`）在画面上看得见，不只是东西在动

## 2. 成片（第 9、10 步）

```sh
bash scripts/contact_sheet.sh out/final.mp4 check/final 5     # 每 5 秒一帧，拼成 3×3 的接触表
```

**一定要从 MP4 文件本身抽帧来检查**，不能只看场景的截图。看完所有接触表，再看脚本打印出的技术指标：
- [ ] **时长**：在要求时长的 ±10% 以内
- [ ] **黑帧**：没有意外出现的黑帧（`black_start`），片头和片尾故意留黑的除外
- [ ] **定格**：没有超过 4 秒的画面静止（`freeze`），除非这个镜头本来就是静止的。如果有，通常是片段比时间轴短、被补帧补长了
- [ ] **逐句有变化**：`python3 scripts/check_sync.py <proj>` 没有 STATIC 的句子。有意停留的镜头在分镜里写了 `hold` 和理由。这个检查只看像素有没有变：镜头缓慢漂移也算“有变化”，所以还要自己看那几秒有没有新信息
- [ ] **响度**：整体约 −16 LUFS，峰值低于 −1 dBTP
- [ ] **音画同步**：随机抽 5 个时间点，用 `ffmpeg -ss <t> -i out/final.mp4 -frames:v 1 check/at_<t>.png` 截图，再对照 `audio/timeline.json` 看那一刻在说哪一句，画面和口播是否一致
- [ ] **字幕**：每行不超过规定字数，没有错别字，和配音内容一致（读音修正的句子显示原文）；英文单词和数字没有被切成两半（例如“Roadste / r”）
- [ ] **读音**：运行过 `check_tts.py`，被标出的句子逐个确认过（多数是转写同音字，不是读错）
- [ ] **音效**：滴答、喷气这些声音和画面上的动作同时发生（时间点来自同一个模型）
- [ ] **开头**：前 3 秒（竖版）或前 8 秒（横版）就出现了问题或最强的画面
- [ ] **结尾**：回答了开头的问题
- [ ] **倒查**：按 `directing.md` 第 9 节逐句对过画面，找过“口播在讲新东西、画面在重复”的时段

## 3. 内容核对

- [ ] 运行过 `python3 scripts/lint_project.py <proj>`，没有 FAIL。它只检查文件之间对得上（事实编号、句子编号、镜头源文件、等级），不检查内容对不对
- [ ] `script.md` 里每个 `{F..}` 都能在 `research/facts.md` 里找到，并且带来源
- [ ] C、D、E、R、S、G、I 等级的内容，口播的说法和画面角标都体现了等级
- [ ] 人物引语都有出处，没有编造的话
- [ ] 口播、画面读数、事实表三处的数字一致：都等于 `model.js` 的 `report()` 输出（口语取整）
- [ ] 用“示意”的地方（典型齿数、推测的结构、中性外观）在画面角落或口播里交代过
- [ ] `brief.md` 里“必须讲清的 3–5 件事”，片子里都讲到了
- [ ] 有时效性的内容，标明了研究日期

## 4. 素材核对（见 `rights.md`）

- [ ] `research/assets.md` 里登记了每一个外部素材（图片、视频、音乐、音效、字体）的来源和授权
- [ ] 需要署名的素材，署名出现在画面上，或者写在片尾
- [ ] 没有真实人物的 AI 生成形象或克隆声音
- [ ] 没有用受版权保护的角色或商标做主画面
- [ ] 开场按 `footage.md` 第 6 节检查过：前 3 秒认得出对象；真实画面和 AI 还原画面一直有署名和角标；引用的版权画面够短

## 5. 检查结论怎么记（check/review.md）

检查的结论分五项写，每项写清**实际看了什么**：

| 项目 | 结论 | 依据 |
|---|---|---|
| 技术 | 通过 / 不通过 | `contact_sheet.sh` 的时长、黑帧、定格、响度 |
| 事实 | 通过 / 不通过 | 第 3 节：编号、来源、等级说法、数字和 `report()` 一致 |
| 讲解（深入浅出） | 1–3 分 | 普通观众看完能不能用自己的话讲出因果；术语有没有当场解释 |
| 叙事 | 1–3 分 | 问题、主线、回答连得上；每个镜头都带来新东西；节奏有变化 |
| 视觉完成度 | 1–3 分 | 风格统一，主体清楚，没有穿插、遮挡、溢出，画面和口播同步 |

打分的标准：3 = 可以交付；2 = 看得懂，但有明显可以改的地方（逐条写出来）；1 = 需要返工。

**没做的检查写“未做”，并写原因，不能当成通过。** 例如：“完整试听：未做。agent 不能听音频，只用 `check_tts.py` 转写核对了读音，语气和节奏没有检查。”“竖版：未做，用户没有要求。”样片和全片各记一份。

## 6. 交付说明怎么写

交付时告诉用户这些内容（简短即可）：
1. 成片路径；竖版剪辑和交互页（如果有）的路径。
2. 片长、画幅，以及在 `choices.md` 里记录的选择。哪些是用户选的，哪些是按推荐默认的。
3. **哪些地方没有核实或者是估算的**，具体到条目。
4. 需要用户自己处理的事：替换占位配音、确认授权、补充署名、**听一遍配音**等。
5. `check/review.md` 里记为“未做”的检查。
6. 工程目录在哪里，以及怎么修改。例如：改某一句的口播，只需重新生成那一句的配音，然后依次运行 timeline、受影响的镜头和 assemble。
